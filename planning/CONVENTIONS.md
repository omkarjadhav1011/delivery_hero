# Planning conventions

The one authoritative definition of how Delivery Hero's plan is laid out, written, checked and carried out. Every skill, subagent and rule points here instead of restating formats. The scripts in `planning/scripts/` enforce what this file defines; if the two disagree, fix whichever is wrong in the same commit.

## 1. Authority

- `docs/` defines the product and is read-only. Planning never edits it. A needed document change becomes a plan task marked "Owner approval needed: changes docs/", applied one change at a time after the owner approves that change. Document problems go to `doc-issues.md`.
- When documents disagree, follow the precedence in `CLAUDE.md` (the Charter's decision log first, a later DEC over an earlier one), and record the conflict in `doc-issues.md`.
- Copy IDs, dates and numbers from the documents or the scripts' output, never from memory.

## 2. Folder layout

```text
planning/

  CONVENTIONS.md          this file
  WORKFLOW.md             the whole /dh workflow for a human reader: phases, states, approvals, recovery

  STATUS.md               generated by status.py
  COVERAGE.md             generated by trace.py: the coverage ledger
  coverage-overrides.md   per-ID ledger classifications (section 8.3)
  owner-actions.md        OA-nn: what only the owner can do
  open-questions.md       Q-nn: what the documents don't settle
  doc-issues.md           DI-nn: problems found in docs/, never fixed there
  check-results.md        results of Verify checks and owner checklists
  checkpoints.md          checkpoint evaluations and the owner's decisions
  plan-changes.md         PC-nn: approved changes to the plan
  environment.md          the production domain and IP, and installed tools
  retrospective.md        after the event (section 21)
  after-v1.md             the later-release backlog (section 21)
  subplans/               one file per subplan (section 5)
  journal/                CURRENT.md and history.md (section 9)
  session-plans/          saved /dh and /dh-plan session plans (section 12)

```

Files are Markdown, except `scripts/` (Python and one Node launcher) and `.cache/`.

## 3. Scripts

Run every script through the launcher, which finds Python 3 on Windows, macOS and Linux:

```bash
node planning/scripts/run.mjs <script> [arguments]
```

Each script has `--help`, prints a short summary, and never needs the model to read its inputs.

| Script | Does | Writes | Exit codes |
|---|---|---|---|
| `state.py` | Works out `/dh`'s state (section 11) | `.cache/gh.json` | Always 0 |
| `phase.py` | Today's phase, rules in force, exit gate, checkpoints and milestones (section 4.2) | nothing | Always 0 |
| `owner.py` | Owner actions due, the next one with its source section, verification and results (section 19) | `owner-actions.md` | 0; 1 overdue or failed; 2 unknown ID; 3 couldn't verify |
| `probe.py` | Checks production from here: DNS, `/health`, redirect, headers, certificate, the latest deploy run (section 20) | `check-results.md` with `--record` | 0 passed; 1 failed; 2 no domain; 3 couldn't check |
| `ids.py` | Indexes every ID in `docs/` | `research/id-index.md`, `.cache/ids.json` | 0; 1 undefined references |
| `docs_manifest.py` | Compares document hashes with the manifest; `--update [DOC ...]` records them | `research/docs-manifest.md` | 0 unchanged; 1 changed; 2 no manifest |
| `section.py <doc> <heading>` | Prints one section (number, title words or an ID); `--list` prints headings | nothing | 0; 2 not found |
| `trace.py` | Builds and checks the ledger both ways (section 8) | `COVERAGE.md` | 0; 1 gaps or problems |
| `validate.py` | Checks subplans, registers and the journal against this file | nothing | 0; 1 errors; 2 no plan |
| `status.py` | Regenerates the tracker (section 7) | `STATUS.md` | 0; 1 needs attention; 2 no plan |
| `next.py` | Lists eligible subplans and tasks, and why others aren't | nothing | 0; 1 nothing eligible; 2 no plan |
| `journal.py` | Keeps the journal and claims (section 9) | `journal/`, Git's `dh-claims/` | 0; 1 differs; 2 idle; 3 blocked by a claim; 4 attempt budget used |

Tests: `python -m unittest discover planning/scripts/tests` (standard library only).

## 4. IDs

### 4.1 Document IDs

`ids.py` defines the families: prefix, home document and meaning. An ID is *defined* where it opens a table row or a heading in its home document; everywhere else it's a reference. Ranges such as `US-01 to US-08` and `OPS-01 to 22` count as every ID in the range.

Two families share the `A-nn` shape. In document 12, `A-01` is an admin screen. Everywhere else it's an assumption, written with its defining document: `A-01@01` (Charter) or `A-09@02` (PRD). Cite assumptions that way in subplans.

### 4.2 Planning IDs

| ID | Meaning | Where |
|---|---|---|
| `P0-01`, `S0-01`, `S1-01`, `S2-01`, `T-01`, `H-01`, `FZ-01`, `E-01`, `AE-01` | Subplans, by phase. `FZ` and `AE` avoid clashing with the documents' `F-nn` features and `A-nn` screens | `subplans/` |
| `S1-03 T4` | Task 4 of subplan S1-03 | the subplan |
| `OA-nn` | Owner action | `owner-actions.md` |
| `Q-nn` | Open question | `open-questions.md` |
| `DI-nn` | Doc issue | `doc-issues.md` |
| `PC-nn` | Plan change | `plan-changes.md` |
| `CP-S0`, `CP-S1`, `CP-T` | Checkpoints (section 15; no `CP-H` since PC-06) | `checkpoints.md` |
| `GNG-1`, `GNG-3` | Go/no-go items only the owner can judge (open Sev-1 or Sev-2 defects; task pool reviewed and loaded) | `check-results.md` |
| `PLAN` | The planning flow's claim | the journal |

Phases and their windows (`phase.py` is the one model; `WORKFLOW.md` shows the full table with rules and exit gates):

| Phase | Name | Dates |
|---|---|---|
| P0 | Owner setup | Thu 24 Sep to Thu 15 Oct (due before the first deploy, DEC-213); owner actions continue later |
| S0 | Walking skeleton | Thu 24 to Tue 29 Sep |
| S1 | Build: core game loop | Wed 30 Sep to Tue 6 Oct |
| S2 | Build: projector, reveal, admin and operations | Wed 7 to Wed 14 Oct; Tue 13 Oct is the load test day on the local stack (`LT` in `phase.py`; DEC-213) |
| T | Trial run | Mon 19 Oct (E−2, DEC-213) |
| H | Hardening | Thu 15 to Mon 19 Oct: the deploy point H-07 and the production checks H-08 before the trial, trial fixes after it; content freeze from Fri 16 Oct |
| FZ | Deployment freeze | Tue 20 Oct |
| E | Event day | Wed 21 Oct |
| AE | After the event | from Thu 22 Oct |

Subplans in T, H, FZ, E and AE start only once their phase has; S phases may run ahead when their dependencies are Done. A `## Phases` table in the master plan (`| Phase | Name | Start | End |`) moves the dates. Every script honors `DH_TODAY=YYYY-MM-DD`, so any date can be tested.

## 5. Subplans

### 5.1 File and heading

`subplans/<phase>-<NN>-<slug>.md`, for example `S0-01-scaffold.md`. The first line is `# <ID> <Title>`.

### 5.2 Field table

```markdown
| Field | Value |
|---|---|
| Status | Not started |
| Phase | S1 (Wed 30 Sep – Tue 6 Oct) |
| Stories | US-13, US-14, or "none (infrastructure)" |
| Priority and points | Must, 6 |
| Depends on | S0-04, OA-03, Q-02, or "none" |
| Unblocks | S1-05 |
| Target dates | Wed 30 Sep – Thu 1 Oct |
| Branch | feat/us-13-start-round |
| Parallel-safe with | S1-06, or "none" |
```

- **Status:** Not started, In progress, In review (pull request open), Done, Blocked (reason in the progress log) or Cut (only with an approved Cut in the ledger).
- **Done** means every task is ticked, the work is merged to `main`, and the subplan's criteria pass. Nothing else counts as Done. Until the first production deploy, the deploy check is on the local stack and production verification waits for H-07 (section 20, DEC-213).
- **Points** are informational: `status.py` computes points from document 04 for the stories listed.
- **Target dates** fall inside the phase's window.

### 5.3 Sections, in this order

Goal · Sources · Context to load · Acceptance · Tasks · Owner actions · Verification · Risks and open questions · Definition of done · Claude Code playbook · Progress log.

- **Context to load:** the exact sections a session reads, as `section.py` calls, for example `section.py 08 5.3`. Never "read document 08".
- **Acceptance:** a table, `| Criterion | Test | Level | Location |`, one row per criterion, copied from document 15.

### 5.4 Tasks

```markdown
- [ ] T1 <what>, in <files or packages>, test first: <test>, source: <IDs and sections>
- [x] T2 ... (ticked only when finished and its test passes)
- [ ] T3 Owner: <what only the owner can do>, test first: none, source: OPS-01, document 16 section 6
- [ ] T4 ..., source: AC-US15-01 (shared) [Blocked: waiting for Q-02]
```

- Every task's source cites at least one document ID, and every criterion of the subplan's stories is cited by a task.
- `(shared)` after an ID marks a shared prerequisite: another subplan owns it.
- `[Blocked: reason]` at the end marks a blocked task. Owner tasks start with `Owner:`.
- Each task is about two hours or less and ends in a committable state.

### 5.5 Progress log

Dated one-line entries: `- 2026-09-30: T1-T3 done; PR #12 open`.

## 6. Registers

Each register is one table with this exact header. `validate.py` checks the headers.

| File | Header | Status values |
|---|---|---|
| `owner-actions.md` | `\| ID \| Action \| Due \| Status \| Unblocks \| Source \| Verify \| Result \|` | Open, Done, Blocked |
| `open-questions.md` | `\| ID \| Question \| Blocks \| Decider \| Due \| Status \| Answer \|` | Open, Answered |
| `doc-issues.md` | `\| ID \| Document and section \| Issue \| Suggested fix \| Blocks \| Status \|` | Open, Accepted, Rejected, Fixed |
| `check-results.md` | `\| ID \| Date \| Result \| By \| Environment \| Notes \|` | Pass, Fail, Blocked |
| `checkpoints.md` | `\| ID \| Date \| Evaluation \| Result \| Decision \|` | free text |
| `plan-changes.md` | `\| ID \| Date \| Change \| Reason and source \| Approved \|` | the approval date |
| `coverage-overrides.md` | `\| ID \| Classification \| Target \| Reason and source \|` | section 8 |

Dates are ISO (`2026-09-30`) or `Wed 30 Sep`. A subplan waiting for an owner action or a question names it in "Depends on". In `check-results.md`, a row whose ID is a subplan ID records that subplan's deploy verification (section 20).

## 7. Master plan and tracker

- `00-master-plan.md` holds the timeline, the dependency graph with the critical path (document 04, section 9), capacity and checkpoint rules, the cut order, parallel work, quality gates, risks mapped to subplans, and owner actions by date. It may hold a `## Phases` table (section 4.2).
- `STATUS.md` is generated by `status.py` and never edited by hand. It has: Summary (needs attention first), Checkpoints, Testing due, Go/no-go (from the trial run on), Subplans, Milestones and Change log.

## 8. Coverage ledger

### 8.1 Classifications

| Classification | Meaning | Status values |
|---|---|---|
| Build | A subplan task builds it; criteria map to their document 15 test | Planned, In progress, Implemented, Tested, Verified in production |
| Verify | A check or procedure scheduled in a subplan | Scheduled, or the latest result from `check-results.md` |
| Covered by | Satisfied through other IDs, which must all resolve to Build or Verify | the least advanced child's status |
| No implementation work | With the reason and source | — |
| Out of scope v1.0 | With the source | — |
| Cut | Only with the owner's approval: the date, the word "approved" and the cut-order source in document 04, section 8 | — |

Build statuses:

- **Planned:** in a subplan.
- **In progress:** the subplan is In progress or In review, or some citing tasks are ticked.
- **Implemented:** every citing task is ticked.
- **Tested:** the criteria pass in the test reports, or the subplan is Done.
- **Verified in production:** the subplan is Done and its deploy is verified on production (section 20): a Pass row under its ID with the environment "production", or, for a subplan Done before the first deploy, H-07's production Pass (DEC-213). A local-stack row never counts. A criterion whose test level in document 15 is Production needs a Pass for the criterion, its test case or its procedure (for example OPS-01).

### 8.2 Family defaults

| Family | Default | Children |
|---|---|---|
| US, EN, AC-US, AC-EN, DS, R | Build | — |
| OPS, MAN, A11Y, LT, TRIAL, E2E, SC | Verify | — |
| F | Covered by | stories whose "Traces to" names it (document 04, section 6) |
| EP | Covered by | the stories in its section of document 04 |
| FR | Covered by | document 04, section 11 |
| NFR | Covered by | document 15, section 16 |
| BR | Covered by | the criteria whose Refs cite it (document 05) |
| UC | Covered by | document 06, section 6 |
| P, S, A (screens) | Covered by | the FRs in the screen's heading and in document 12, section 12 |
| TC-US, TC-EN | Covered by | the criterion with the same number |
| DEC and the decision families (PD, SD, HD, LD, AD, ADR, AP, DB, UX, CS, GS, TP, DG, SG, CL), QA, TD, OI, ASM, C, OBJ | No implementation work | — |
| W | Out of scope v1.0 | — |

A decision that needs direct work (for example DEC-196, the Surefire report setting) gets an override to Build, and a task cites it.

### 8.3 Overrides

`coverage-overrides.md` holds one row per exception. `Target` lists children for Covered by, or the subplan and task for Build. `COVERAGE.md` is regenerated on every run, so never edit it; change the plan or the overrides instead.

### 8.4 Rules `trace.py` enforces

- Every ID appears once and is classified; unknown families are errors.
- Every Build and Verify ID is cited by a subplan task (stories by a subplan's Stories field and all their criteria by tasks).
- Every Covered-by ID resolves to Build or Verify leaves that are planned. A PRD feature or epic with no story is a doc issue to raise with the owner, never dropped silently.
- Every task cites at least one ID, and every cited ID exists.
- No ID is owned by two subplans unless all but one citation is `(shared)`.
- A Cut subplan's IDs need approved Cut overrides.

## 9. Journal and claims

### 9.1 `journal/CURRENT.md`

Written only by `journal.py`, and under 60 lines: a field table (State, Session, Subplan, Branch, Start commit, Last commit, Step, Task, Attempts, Started, Updated, Next action) and four lists (Completed tasks, Pending approvals, Failing tests, Notes). State is `idle` or `active`.

Steps: preflight, planning, plan-session, awaiting-approval, test-first, implement, check, e2e, review, wrap-up, resume.

### 9.2 When to write it

At every step change, and before and after each task:

1. `journal.py start <subplan> --next "..."` claims the subplan and opens the session.
2. `journal.py step <step> --next "..."` at each step change.
3. `journal.py task T4 --next "..."` before a task; `journal.py attempt --test <name> --error "<first line>"` after each failed run; `journal.py fail-clear` when it passes.
4. Commit the task, then `journal.py done T4 --commit <sha> --next "..."`.
5. `journal.py approval add "..."` before stopping for the owner; `approval clear` after the answer.
6. `journal.py end --summary "..." --outcome done|paused|blocked` appends to `history.md`, releases the claim and resets `CURRENT.md`.

The next action is always concrete: the command to run or the file and test to write next.

### 9.3 Commit per task

Commit after each completed task on the feature branch, for example `wip(S1-03): T4 start-round countdown`, with the task's code, tests, the ticked checkbox and the progress-log line together. An interruption then loses at most the task in progress. The pull request's squash title uses the normal Conventional Commit form.

### 9.4 Attempt budget

A test that still fails after 3 focused attempts stops the task: `journal.py attempt` exits 4. Mark the task `[Blocked: ...]` with the evidence (test name, first error line, what was tried), propose options, and ask the owner.

### 9.5 Claims

A claim is a file in Git's common directory (`.git/dh-claims/<subplan>.json`), so every worktree sees it, created atomically. One active claim per subplan. A claim with no journal activity for 24 hours is stale: `journal.py release <subplan> --force` removes it, only with the owner's approval.

## 10. Resume protocol

Used by `/dh` in state 3, by `/dh resume`, and after `/clear`, compaction or an interrupted turn:

1. **Read the journal:** `journal.py show`.
2. **Compare it with Git:** `journal.py check` reports the branch, the last commit, commits made since, uncommitted files, the claim and staleness.
3. **Rerun** the failing test, or the last task's test.
4. **Continue** from the next action if everything agrees. If anything differs, show the differences and ask the owner. Never discard uncommitted work without the owner's approval.

## 11. The `/dh` states

`state.py` reports every state that applies; the lowest-numbered one is primary. State 6 is primary only when a checkpoint is due and unrecorded, or on the trial run and event days, when the phase's mode takes over. Otherwise the phase's rules and freezes constrain the later states.

| # | State | Detected by | Action |
|---|---|---|---|
| 1 | Preflight problem | merge, rebase, cherry-pick or interrupted commit; detached HEAD; conflicts; hook self-test fails; Git or Node missing | Explain and stop. Missing Docker, `gh` or `npx` degrades instead: unit tests only, integration tests pending |
| 2 | No plan | no `planning/subplans/` | The `/plan-implementation` flow, then the manifest, ledger and status |
| 3 | Unfinished session | the journal is active | The resume protocol |
| 4 | Documents changed | `docs_manifest.py` | Subagents read the changed documents in full; impact analysis; proposed plan changes |
| 5 | Plan invalid or with gaps | `validate.py` or `trace.py` | Show the problems; propose fixes |
| 6 | Phase rule or checkpoint applies | `phase.py` and section 15 | Evaluate with numbers; the phase's mode (trial, event); propose cuts or reordering |
| 7 | CI red on `main` | the last CI run on `main` failed | Offer to fix it first |
| 8 | Owner actions due | `owner.py`: overdue, or due by tomorrow | Owner-checklist mode (section 19) |
| 9 | Ready to work | `next.py` | Present the status and the recommended work; ask |

## 12. Session plans

`session-plans/YYYY-MM-DD-HHMM-<focus>.md`, with these sections: **Context** (focus, state, reading mode, branch and commit), **Report** (the status or `dh-planner` report), **Choice** (what the owner chose, and when), **Result** (filled in at the end: commits, files, what wasn't done and why).

## 13. Plan-change procedure

1. **Propose:** list each change (what, why, the source IDs, the subplans and ledger rows affected). Nothing changes yet.
2. **Approve:** the owner approves each change, or rejects it.
3. **Apply** the approved changes: subplans, registers or `coverage-overrides.md`. Add a row to `plan-changes.md` and a progress-log line to each affected subplan.
4. **Check:** `validate.py`, `trace.py` and `status.py` must pass, or show remaining gaps for the owner.
5. **Commit:** `docs(planning): <change>`.

Cuts follow the cut order in document 04, section 8, and are only recommendations until the owner approves them. A request outside the plan becomes a proposed plan change with its source, or a question, never unplanned work.

## 14. Testing built into the flow

| When | What | How |
|---|---|---|
| Each task | Unit and integration tests for its criteria, written first | the task's `test first:`; without Docker, integration tests are recorded as pending |
| Each session | `/check` | before the wrap-up |
| When the subplan or the schedule says | `/e2e` | the subplan's Verification, document 15, section 18 |
| After test runs | `tools/ac_coverage.py` | read by `status.py` and `trace.py` |
| At their dates | OPS, MAN, A11Y, LT and TRIAL procedures | `status.py` "Testing due"; owner checks are presented as checklists, and results go into `check-results.md` |
| From the trial run | Go/no-go view (document 14, section 11) | `status.py`; evidence from `check-results.md` and the coverage report |

## 15. Freezes and checkpoints

- **CP-S0** (Tue 29 Sep), the capacity check in document 04, section 8: S0 points done ÷ S0 working days × working days left before the trial run, compared with the open Must points.
- **CP-S1** (Tue 6 Oct): any S1 Must story unfinished triggers the cut order.
- **CP-T** (Mon 19 Oct, DEC-213): go/no-go. A no-go moves the event date (A-01); there is no re-check (DEC-215).
- A checkpoint's evaluation and the owner's decision go into `checkpoints.md`. Until they do, `/dh` stops at state 6.
- **Content freeze** from Fri 16 Oct: task content edits only fix errors. **Deployment freeze** from Tue 20 Oct: merges only for problems that would stop the event. **Event day** (Wed 21 Oct): no merges; the deploy lock must be verified.

## 16. Approval points

Always stop for the owner's approval before:

- the plan outline;
- each session plan;
- any change to the plan, the ledger classification or a cut;
- any change to `docs/`, one change at a time;
- discarding work;
- `git push` (including tag pushes such as `v1.0.0`), `gh pr create`, and anything destructive.

Merging is always the owner's, because a merge deploys to production (from H-07; until then the Deploy workflow is disabled, DEC-213).

## 17. Token rules

- Scripts do the counting, indexing, validation and status. Read their short output, not their inputs.
- Read document sections with `section.py` and the subplan's "Context to load", never whole documents in routine work. Read whole documents only when one changed, and then in a subagent that returns a compact summary.
- Heavy analysis runs in subagents that return summaries.
- Keep skill bodies short; detail lives here or in files read only when needed.
- One subplan per session. The journal and progress logs carry state between sessions, never the conversation.
- Don't reread a file already in context unless it changed.

## 18. Git

- Branch per subplan, as its Branch field says; never commit on `main`.
- Planning-only changes: `docs(planning): ...`. Task commits: `wip(<subplan>): T<n> ...`. Pull request titles use Conventional Commits, and merges are squash only.
- Push and pull requests only after the owner approves; the owner merges.

## 19. Owner checklists

- `owner-actions.md` holds everything only the owner can do: a due date, what it unblocks, its source section, and a `Verify` value (`none`, `dns`, `health`, `redirect`, `headers`, `cert` or `deploy`).
- `/dh owner` takes one action at a time:
  1. `owner.py next --show` prints the action and its source section.
  2. The owner does it.
  3. `owner.py verify <ID>` runs the `probe.py` check where one exists. For `none`, record what the owner reports.
  4. `owner.py record <ID> --status Done --result "<what was verified or reported>"`.
- Never ask the owner to paste secrets. Record only what's safe to commit: the domain, the public IP, the region, "done".
- Owner checklists for checks (OPS, MAN, A11Y, TRIAL, LT, GNG-1, GNG-3) show the steps from document 15 with `section.py`. Their results go into `check-results.md`.

## 20. Deploy verification

After the owner merges a subplan's pull request:

**Until the first production deploy (DEC-213)** the Deploy workflow is disabled (OA-28). After a merge, verify on the local stack instead: `/check` and `/e2e` on the merged `main`, then a progress-log line "verified on the local stack at <sha>", and set the subplan to Done. Don't record it under the subplan ID in `check-results.md`. Production verification for every subplan Done before then happens once, at the deploy point H-07. From H-07 on, the steps below apply.

1. `probe.py deploy --sha <merge commit>` reads the Deploy run on `main`:
   - exit 0: deployed;
   - exit 1: failed and rolled back, so the previous release is running;
   - exit 75: stopped because a game is in progress, with nothing restarted (re-run the job after Results or Closed);
   - failed before deploying: the build or tests failed;
   - no run: a merge touching only `docs/`, `planning/` or `.claude/` doesn't deploy, and none runs while the workflow is disabled (DEC-213).

   Without the GitHub CLI, ask the owner for the run's result.
2. `probe.py all --record` checks `/health`, the redirect, the headers and the certificate on the domain in `environment.md`.
3. Record the verification, with `probe.py deploy --record --subplan <ID>` or a manual row under the subplan ID in `check-results.md`, and set the subplan to Done. The ledger then shows Verified in production (section 8.1).

## 21. Release, event and after the event

- **Release (FZ, `/dh release`):**
  - the final regression and the coverage report with `--strict-must`;
  - the day-before checklist in document 16, section 11.1;
  - OPS-16, OPS-19 and OPS-22;
  - the `v1.0.0` tag per document 13, section 9.6. Tag locally; pushing the tag needs the owner's approval.
- **Document 17** (release notes): a hardening task marked "Owner approval needed: changes docs/".
- **Event (E, `/dh event`):** runbook mode from document 16, sections 11.1 and 12 to 14.
  - The on-the-day and hour-before steps, with contingencies: the laptop's hotspot (R-07), a stopped instance (start it in the console), rollback, and postponing (A-01@01).
  - No code changes and no merges.
  - Incidents go into the journal's notes and, after the event, the retrospective.
- **After the event (AE, `/dh retro`):** close the game, check past games, run OPS-13 and the backup check, then the survey (E+1) and its results (E+6).
- **`retrospective.md`** sections: Summary, What went well, What didn't, Incidents (with times), Metrics (players, join times, load test, defects by severity, SC-1 and SC-2), Actions.
- **`after-v1.md`:** one row per item, `| Item | Source | Why deferred | Priority |`. It starts with W-01 to W-06, the Cut stories, and the known Sev-3 and Sev-4 issues.
- **Archiving:** the ledger's final statuses come from `trace.py`. The plan is archived by recording the final `status.py` and `trace.py` summaries in the retrospective.
